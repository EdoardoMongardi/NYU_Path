CORE PHILOSOPHY OF PROJECT you need to keep in memory whenever dealing with NYU PATH(update it if previous philosophy differs from this one):

One sentence:
Essentially the agent behavior should be very similar to a professional human college advisor for all NYU undergrad students(including NYU Shanghai and NYU Abudabi).

Source of data:
Conclusions/decision/suggestions all must come from finding relevant info from the bulletin data(policies, qualitative data, info/rules/data that is not structured in the system but required to answer questions, etc); read the DPR of the student to retrieve the real personalized info(course taken, grade taken, rule satisfaction, remaining requirements, grades etc). See the sample DPR pdf in the repo, never guess structure), ask the student for their goal/expectations/preference(goal graduation semester, course preference, work load preference/distribution of semesters, study abroad/honor programs or courses preference, summer/J-term preference etc), and then use that info to come to a conclusion/decisions/suggestions. Whenever conclusion/decisions/suggestions cannot be 99% + grounded/computed, it should output a confidence level and inform the student with key points they need to verify/confirm with their human advisor. Identify risk and/or state trade-offs of agent-proposed/student-proposed decisions whenever it is necessary to let the student know.


Course planning (core functionality):
The course planning should be deterministic on validity considering all possible aspects. When planning for semesters when FOSE is available: also consider course availability(waitlist,closed,open. If a waitlist course is a must or student strongly suggest to take it, identify the waitlist number if that data is available and suggest the best approach such as register for a open course and stay in waitlist for the desired course, albert has a mechanism of "auto swap", which automatically swaps a waitlisted course with a registered course when it became available; closed courses will not open anymore for that semester), avoid time conflicts between courses, consider campus locations, instruction modes, instructor preference (hard to compare without other sources but can let the student decide), recitation section planning(still considers availability and avoid time conflict) and all other live data that is relevant to planning, etc. For further future semesters, plan with structure(because no live data is available) but still considers all other aspects/data that are available without live FOSE API, such as course name, semesters offered, prerequisite check, rule satisfactions, campus offered, work load balance(in this project, only free electives are considered easy, major required courses/major electives/school required core courses such as CAS CORE are considered heavy load, the agent should evenly distribute "heavy" courses and "easy" courses to all remaining semesters as much as possible, unless the student specifically specify other distribution or work-load acceptance), etc. So in this manner, the course planning should be able to identify what schedule is "valid"(does not surpass student goal graduation semester, does not break F1 status if international student, satisfies all degree requirements, etc) and what schedule is "preferred" by the student(consider all other aspects that is relevant with the student's personal goal/preferrence such as specific course preference, different work-load distribution preference, specific instructor preference, course instruction preference, content of courses preference, study abroad/summer/J-term preference, honor program preference, etc). All plans/schedule MUST be "valid". "valid plans" may have more than one, so the suggested plan for the student need to satisfy the student's preference as much as possible but must not make it not "valid". Student may not claim all preferences so we need to have defaults for all preference fields we consider, change these fields whenever a student claims it. Student may also specify a specific schedule that breaks their claimed preference, that has the highest priority. Student may claim preferences that we did not structured, use LLM to adjust as much as possible. So to wrap up, the planning flow should look like:

1. Identify all info in order to make the plan "valid"
2. Apply all known student preference to output a "best" plan for the student(still must be "valid").
3. If student claims/update preferences though chat, output the new plan with updated preferences.
4. If student specify a specific change on the suggested plan, verify if it is valid. If "valid", change accordingly and claim trade-offs comparing with the previous plan. If not "valid", refuse the change and state why cannot change.
5. When student "confirms"(using a UI button), store this plan in the user's database.
Notes: all courses shown in the DPR that does not have the status "IP"(in progress), student cannot modify it because these courses are already taken and the status is final. But student can instruct the agent to change any courses/plan that has the status "IP" or is only planned(future terms that is planned by the agent) — subject to the IP-window nuance below. The agent should be able to answer questions about why a specific plan is planned in this manner ( e.g. because this make it valid, because this align with your preference of xxx, etc)

DPR is the single source of truth for the fields it shows deterministically — the home school, declared major/minor, catalog year, courses taken, and grades. The student CANNOT change any of these by asking the agent or via the onboarding wizard; to change them the student must upload a corrected/new DPR that shows them differently, and the agent should ask for that re-upload rather than ever force-changing the value or fabricating one (e.g. never invent a grade). Only fields that are NOT on the DPR — visa / F-1-vs-domestic status, and all preferences — may be changed via a UI control (button/bubble) or an agent ask-confirm-change flow. Exception: if a DPR-derived field genuinely cannot be read off the DPR (e.g. the home school has no clear indicator), only THEN may the agent ask the student to supply it as a fallback.

IP-course changeability is window-aware, not blanket-modifiable. A course with a FINAL grade is absolutely unmodifiable. A course enrolled for a FUTURE term (pre-registered, still IP) is freely changeable — it is only planning, with no real-world registration to undo. A CURRENT-term IP course can in reality still be dropped only within the registrar's add/drop window; after that it can be withdrawn (a "W", which does NOT fulfill the requirement) or, where allowed, taken pass/fail (a "P"/"F" that may not satisfy a letter-grade major rule) until a later withdrawal deadline, after which it is effectively locked into its grade. The exact deadlines shift every year and the system holds only typical/assumed per-season dates, so any conclusion about a current-term course's changeability carries a confidence level + "verify the exact deadline with your adviser." Crucially, a drop / withdraw / pass-fail does NOT appear on the DPR until the next DPR is uploaded — so any current-term change the student CLAIMS to have made is an UNVERIFIED assumption: the agent may plan around it only as a clearly-marked draft / what-if (surfacing the consequences and the hedge), but never records it as fact and never invents the resulting status or grade.

Policies retrieval:
These are questions regarding general policy explanations, the system should be able to find relevant info(sometimes could be multiple sections in the bulletin data) of policies to answer the student's general policy questions. Whenever a course planning cannot decide on something, cannot find relevant rule or data, or it is not currently structured on something, it could also make use of this functionality to get better context to allow the LLM to do refinements on the plan or help explain with the "why" and "how" questions.
