# Planning Engine — Phase 3: Advisor Agent

> Drafted 2026-06-10. Status: plan (granularizes design spec §6). Source: Docs/specs/2026-06-05-planning-engine-rebuild-design.md §6/§7.4/§10/§11.

**Goal.** Phases 0–2 (feasibility-first constraint search + the 7-axis graduation-path validator + 20 tools) are DONE and merged. Phase 3 builds the **conversational advisor layer ON TOP of the finished engine — it adds NO new solver capability.** It makes the agent behave like a human academic adviser: **explain *why* each course is placed (and which are locked vs movable), surface risk and trade-offs proactively on both agent- and student-proposed decisions, attach confidence + "verify with your adviser" whenever a conclusion is not ~99% grounded, and proactively elicit goals/preferences** — all while keeping the engine's contract intact. The launch-blocking exit criterion is the second clause of design §10: **"ungrounded plan claims blocked"** — the response validator must catch a reply that claims a course is in a term, or that the student graduates in a term, when the stored `session.forwardSchedule` says otherwise. Everything else rolls into the first clause, "agent eval cases pass." The north-star is `Docs/core_philosophy.md`: human-advisor parity for ALL NYU undergrad (Washington Square + Shanghai + Abu Dhabi — NOT CAS-only), deterministic-on-validity then preferred, never produce an invalid plan or a fabricated claim.

### D2 — Counterfactual probe (read-only re-solve with an injected constraint)
*Design §6 Toolbox: "counterfactual probe (re-solve with a constraint: can I / why not / how do I / what if I fail X)"; §3 lists it as NEW. Mechanism per §7.3: apply the change as a constraint → re-solve → validate → valid? diff + trade-offs; invalid? refuse + explain the binding constraint. **Read-only what-if, distinct from the mutation/confirm path (design §2 decision #5: edits are never instant).** A GENERAL primitive, NOT per-question routing.*

- **D2.1 — `probe_counterfactual` tool (general constraint injection — TWO arms, distinct substrate).** *Goal:* a new read-only tool that takes a structured counterfactual and re-solves through the 7-axis `runGraduationPathValidator`, returning a diff + (when infeasible) the binding-constraint explanation. **The two probe families have DIFFERENT substrate and must NOT be conflated:**
  - **Arm A — future-course (add/forbid/move a not-yet-taken course or a term).** Reuses the SAME preference-override re-solve path `proposePlanChange.ts:127-158` uses: express the counterfactual as an exclusion/pin/addTerm on a non-mutating `preferencesOverride` (`buildSolverInput.ts:80-86`) → `buildSolverInputWithRulesFromSession` → `finalizeForwardSchedule`. This is the existing seam — note that `excludedCourseIds` (`materializePlan.ts:336-337`) only blocks FUTURE placement; it cannot un-complete a passed course.
  - **Arm B — fail/drop a COMPLETED course (the headline "what if I fail CSCI-UA 101").** This is **NET-NEW substrate, NOT a reuse of proposePlanChange's path.** Preferences cannot model it: `coursesTaken` is built ONLY from `dpr.courseHistory` rows passing the grade threshold (`buildSolverInput.ts:196-206`) and `unmetRequirements` ONLY from `notSatisfiedRequirements(dpr.requirementGroups)` (`:234`); a "fail" must un-complete the passed row AND re-open its satisfied requirement, neither reachable from `preferencesOverride`. Add a NEW DPR-transform injection point: before `buildSolverInput`, derive a synthetic `DegreeProgressReport` where the named course's `courseHistory` row is moved passed→failed (so `notSatisfiedRequirements` re-includes its requirement group and `coursesTaken` excludes it), then re-solve on that synthetic DPR. Add a `BuildSolverInputOpts.dprOverride` (or `coursesTakenOverride`) seam at `buildSolverInput.ts:72-86` — there is none today (`SolverInput.coursesTaken` is a plain `Set<string>` with no override, `forwardSchedule/types.ts:49`). Keep this DISTINCT from the closed `PlanMutation` union, which cannot express it. *Failing test (red):* `tests/agent/tools/probeCounterfactual.test.ts` — (a) **Arm B:** "what if I fail CSCI-UA 101" on a DPR where 101 is a passed row → assert the synthetic-DPR re-solve re-opens 101's requirement (`coursesTaken` no longer contains it) and surfaces cascaded shifts / new unmet requirements; (a2) **Arm A:** "what if I can't take CSCI-UA 102 next term" → exclusion-override re-solve shifts the placement; (b) byte-identical session after either call (`isReadOnly: true`, no write to `session.forwardSchedule`/`schedulePreferences`/the real DPR); (c) an infeasible probe returns `conflicts` sourced from `infeasibilityReport.conflictSource`/`conflictDetail`, not a coarse solver flag. *Seam:* new `tools/probeCounterfactual.ts` (register in `registry.ts:67-88`); Arm A reuses `finalizeForwardSchedule` via `preferencesOverride`; Arm B adds the `dprOverride` injection point + a pure `applyFailedCourseToDpr(dpr, courseId)` transform; both run `runGraduationPathValidator`; **choose rigor explicitly** — placeholders count as satisfiers + credit floors are null-gated, so the probe must set rigor like the build path (PLAN-4), NOT trust the solver's coarse `derivePlanState`. *Green:* both arms read-only + 7-axis-validated + binding-constraint explained; the DPR transform never mutates `session`. *Dependency:* P3.1 (needs a hydrated plan to probe against).
- **D2.2 — "why not Z" framing.** *Goal:* the tool's output distinguishes "valid but with trade-offs" from "infeasible because \<failing axis + reason\>" so the agent can answer "why can't I take Z next term?" honestly. **Honest scope of what the engine emits today:** `graduationPathValidator.ts:614-626` ALWAYS sets `conflictSource: 'other'`, `conflictDetail: \`Axes failed: <axis>: <reason>\``, and `relaxationSuggestions: []` — it never maps the failure back to the injected counterfactual (no "failing 101 breaks the prereq chain for 102" causal string), and the `conflictSource` enum (`shared/types.ts:1065`) is never set to anything but `'other'` here. So D2.2's acceptance is the **failing-axis + reason** string the validator actually produces, NOT a course-causal binding-constraint sentence. *Failing test (red):* extend D2.1's test — a probe the validator rejects yields the human-readable failing-axis-and-reason string from `infeasibilityReport.conflictDetail`; a probe that passes-with-trade-offs yields the trade-off diff (D3 path). *Seam:* `summarizeResult` on the new tool. *(Optional follow-on, NOT a D2.2 prerequisite: enrich `infeasibilityReport` to map the injected counterfactual to a non-`'other'` `conflictSource` + a causal `conflictDetail` — scope as a separate engine task if the owner wants the course-causal phrasing.)* *Dependency:* D2.1, D3.1.

D1's richer summary + D4's added prompt rules grow the context — watch the token budget; the new D5 check participates in the existing replay-buffer gate automatically (no loop surgery), but a truncated reply could still slip a plan claim if the context blows. - Scoped commit: `git add <explicit files>` (**never `-A`**); message trailer:
  `Co-Authored-By: Claude Opus 4.8 (1M context) <noreply@anthropic.com>`
